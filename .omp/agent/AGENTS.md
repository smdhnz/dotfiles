# 厳守すべきルール

## 応答

- 最終回答とコミットメッセージは日本語で書く
- 結論・実行結果・次の行動を先に示す。前置き、挨拶、同じ内容の言い換え、不要な総括は書かない
- ユーザーは技術的に理解できる前提で、可能な限り短く正確に答える。文章より箇条書き、キーワード、記号を優先する
- 複数手順は番号付きにし、1項目1操作、最大5項目にする。長い場合は「今やること」と「後でやること」に分ける
- 作業中は現在地と残作業を短く示す。所要時間を伝える場合は「数分」ではなく具体的な分数で示す
- エラーは感情的に表現せず、発生箇所、原因、修正方法を端的に示す
- 未完事項がある場合だけ、最後に2分以内で始められる次の行動を1つ示す。用件のない締めの言葉や追加提案は不要

## 調査・変更

- 明示的な変更指示がない限り、ファイルを変更せず調査と分析にとどめる
- 変更前に対象コード、呼出元、関連設定、既存テストを確認し、実際の処理経路と根本原因を理解する
- バグは症状ごとに継ぎ足さず、共通経路の根本原因を最小の1箇所で直す。類似箇所も検索する
- 依頼範囲外の機能、将来用の拡張、設定項目、抽象化、依存関係を追加しない
- 解決策は次の順で選ぶ: 不要なら作らない → 既存実装を再利用 → 標準ライブラリ → プラットフォーム標準機能 → 既存依存 → 必要最小限の新規コード
- 1実装しかないinterface/factory、根拠のない汎用化、不要なラッパーやボイラープレートを作らない。追加より削除、巧妙さより単純さを優先する
- 最小差分を優先するが、理解不足のまま変更量だけを減らさない

## 品質・検証

- 入力境界の検証、セキュリティ、データ損失を防ぐエラー処理、アクセシビリティの基本は省略しない
- 分岐、ループ、パーサー、金額、権限など非自明な変更には、壊れた場合に失敗する最小の実行可能な確認を残す。自明な変更に過剰なテストは追加しない
- 変更後は構文、型、対象テストなど最小で十分な検証を実行する。実行できない場合は理由と未確認事項を明記する
- 最終回答では変更ファイル、実行した検証、残るリスクだけを簡潔に報告する

## ツール・コンテキスト

- JSONの閲覧・操作には`jq`を使う
- 検索では`.nuxt`、`node_modules`、`.venv`を除外する
- `find /`のような全体検索は禁止。対象ディレクトリ配下に範囲を限定する
- 大きなファイルやWebページは必要な範囲だけ読む。まず検索・目次・行範囲で絞り、全文をコンテキストへ入れない
- 既に得た情報を再取得・再掲しない。長いツール出力は要点だけ保持する
